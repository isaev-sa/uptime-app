# Code review

Ревьюй запрошенные изменения; не исправляй код без отдельного запроса. Прочитай применимые AGENTS.md и [чек-лист](references/review-checklist.md), включая архитектуру проекта. Оцени каждый применимый пункт по изменённому коду и необходимому окружающему контексту; неприменимые разделы пропускай. Инструменты не заменяют ручной анализ.

1. Определи область ревью из запроса. Для указанного коммита используй `git show --format=fuller --stat <commit>` и `git diff <commit>^ <commit>` (для корневого коммита — `git show --format= --root <commit>`). Для ветки сравни её с указанной базой или локальной основной веткой через `git diff <base>...HEAD`. Если запрошены локальные изменения, изучи `git diff`, `git diff --cached` и `git status --short`; прочитай также неотслеживаемые файлы в области запроса. Без уточнения области выбери локальные изменения, если они есть, иначе сравни ветку с основной; на основной ветке без локальных изменений ревьюй последний коммит. Не делай fetch и не переключай ветки без необходимости. Для merge-коммита выясни нужную базу; не подменяй её произвольным родителем. Учитывай удаления и переименования.
2. До ручного ревью запусти из корня репозитория `bash .codex/skills/code-review/scripts/static-checks.sh` с `--backend` и/или `--frontend` в соответствии с затронутыми файлами. Для общих файлов оцени влияние на оба проекта; если ни один не затронут, укажи это. Скрипт проверяет текущее рабочее дерево, а не исторический diff: если оно не соответствует ревьюируемой версии, сообщи об ограничении и при возможности проверь нужную версию в отдельном безопасном окружении. Не устанавливай зависимости автоматически. Зафиксируй выполненные, упавшие и пропущенные проверки; пропуск не считай успехом.
3. Пройди общие пункты чек-листа и разделы по затронутым областям. Проследи последствия изменений через вызовы, контракты и тесты. Для изменённых API проверь согласованность frontend/backend и документации. Проверяй секреты также в конфигурации и добавленных файлах; не выводи значения найденных секретов.
4. Сообщи только конкретные, вызванные изменением проблемы с воспроизводимым сценарием и влиянием, не выдавай догадки за факты. Не создавай замечания только ради выполнения пункта чек-листа. При необходимости укажи неопределённость или риск отдельно.

## Результат

Сначала замечания по убыванию срочности: **P0** — немедленная критическая угроза безопасности, потеря данных или недоступность основной функции; **P1** — серьёзная уязвимость или сбой существенного сценария; **P2** — воспроизводимая ошибка или значимый пробел надёжности; **P3** — ограниченная проблема поддержки, качества или удобства; **P4 и ниже** — подтверждённые малозначительные проблемы. Приоритет зависит от фактического влияния и вероятности, а не только категории. Для каждого замечания укажи `[P<n>]`, краткое название, файл и минимальный диапазон строк, условие возникновения, последствия и направление исправления. Привязывай замечание к изменённым строкам, когда возможно. Затем перечисли допущения и результаты/ограничения проверок. Если замечаний нет, скажи об этом явно и укажи остаточные риски и непроверенные сценарии.
