# Миграции базы данных

Этот гайд предназначен для разработки и проверки изменений схемы PostgreSQL, в том числе агентами. Команды выполняются из корня репозитория, если не указано иное.

## Где что находится и как работает

- `backend/internal/storage/migrations/` — последовательные SQL-файлы миграций, например `001_initial.sql` и `002_user_name.sql`.
- `backend/internal/storage/storage.go` — загрузка файлов через `go:embed` и функция `storage.Migrate`.
- `backend/cmd/server/main.go` — вызов миграций при запуске до начала обработки HTTP-запросов.
- `schema_migrations` в текущей схеме PostgreSQL — журнал: полное имя файла в `version` и время применения в `applied_at`.
- `backend/internal/auth/integration_test.go` и `controller_integration_test.go` — примеры интеграционных тестов с отдельной схемой.

При запуске сервер сортирует имена файлов лексикографически и выполняет отсутствующие в журнале `.sql`-файлы. Все новые миграции одного запуска и записи в журнале выполняются в одной транзакции под advisory lock. При ошибке транзакция откатывается, а сервер не запускается. Уже записанные файлы не выполняются повторно; их содержимое и контрольные суммы не проверяются. Откатных миграций и отдельной команды миграции в проекте сейчас нет. SQL встраивается в бинарный файл при сборке, поэтому для доставки нового файла нужно пересобрать приложение или образ.

## Добавление миграции

1. Изучите текущие файлы, модели и запросы, которые затрагивает изменение. Выберите следующий свободный номер после последнего файла; сохраняйте ведущие нули, чтобы лексикографический порядок совпадал с порядком применения. Проверьте номер ещё раз после обновления ветки: параллельная работа может занять его.
2. Создайте `backend/internal/storage/migrations/NNN_kratkoe_opisanie.sql`. Не редактируйте и не переименовывайте уже применённые миграции: исправления оформляйте новым файлом. Не используйте GORM `AutoMigrate` для изменения схемы.
3. Напишите PostgreSQL SQL с учётом существующих данных. Например, при добавлении обязательного поля сначала добавьте допускающий `NULL` столбец, заполните существующие строки и только затем установите `NOT NULL` (см. `002_user_name.sql`). Добавьте необходимые ограничения и индексы. Все операции должны поддерживать выполнение внутри транзакции; например, `CREATE INDEX CONCURRENTLY` здесь использовать нельзя.
4. Обновите связанные модели, запросы и поведение приложения. Для преобразования данных или изменения ограничений добавьте осмысленные интеграционные проверки как для пустой базы, так и для базы с данными до миграции. Учитывайте совместимость старой и новой версий приложения при развёртывании и заранее продумайте восстановление данных: автоматического `down` нет.

Шаблон файла (имя и SQL замените под задачу):

```sql
-- NNN_add_example.sql
ALTER TABLE users ADD COLUMN example TEXT;
UPDATE users SET example = 'initial' WHERE example IS NULL;
ALTER TABLE users ALTER COLUMN example SET NOT NULL;
```

## Проверка

1. Из `backend/` выполните `go test ./...` и `go build ./...`. Без `TEST_DATABASE_URL` PostgreSQL-интеграционные тесты пропускаются — успешный запуск сам по себе не подтверждает работу миграций.
2. Запустите их с отдельной тестовой базой PostgreSQL и правом `CREATE` на неё:

   ```sh
   cd backend
   TEST_DATABASE_URL='postgres://USER:PASSWORD@HOST:5432/TEST_DB?sslmode=disable' go test -count=1 -v ./...
   ```

   Проверьте в выводе, что интеграционные тесты не пропущены. Они создают и удаляют временные схемы; `TestPostgresIntegration` также повторно вызывает `Migrate`. Вернитесь в корень репозитория для следующих команд.
3. Проверьте обновление на отдельной базе с предыдущей версией схемы и представительными данными: запустите предыдущую версию приложения, создайте данные, затем запустите пересобранную новую версию с тем же `DATABASE_URL`. Убедитесь, что данные сохранились и преобразованы правильно, новые ограничения и запросы работают, а повторный запуск не меняет результат. Интеграционные тесты на пустой схеме не заменяют эту проверку.
4. Проверьте журнал и фактическую схему в тестовой базе. Например, при локальном Compose после `docker compose up --build` с заданным `JWT_SECRET`:

   ```sh
   docker compose exec db psql -U uptime -d uptime -c 'SELECT version, applied_at FROM schema_migrations ORDER BY version;'
   docker compose exec db psql -U uptime -d uptime -c '\d users'
   ```

   Сравните список версий с файлами и проверьте изменённые таблицы, индексы, ограничения и данные запросами, соответствующими миграции. Compose использует постоянный том `postgres_data`, поэтому для проверки с нуля используйте отдельную тестовую базу или изолированное окружение; не удаляйте существующий том ради проверки.

## Если миграция завершилась ошибкой

Найдите имя файла и ошибку SQL в логах сервера, проверьте подключение, права, данные и журнал `schema_migrations`. Исправьте причину и повторите запуск: изменения всех миграций, выполнявшихся в неудачной транзакции, должны быть откачены. Если файл уже был успешно применён где-либо, не меняйте его: подготовьте следующую корректирующую миграцию. Перед работой с важной базой подготовьте и проверьте резервную копию и план восстановления; не удаляйте записи журнала и не меняйте схему вручную без понимания последствий.
